**Takeaways for the comparison table**

1. **Only two of the seven are closed-loop policy benchmarks in sim** (roto 2.0, SoftVTBench). EgoTactile, RCT, HT-Bench, HRDexDB are datasets/perception benchmarks with no policy; TactiDex is hybrid (real data → sim RL → real deploy).
2. **Tactile is a policy input in exactly three**: roto 2.0 (tactile-only), SoftVTBench (visuo-tactile variants), TactiDex (tactile as reward + privileged critic signal, not deployable feedback). None of them train a *visuo-tactile VLA-style policy across heterogeneous hands*.
3. **Cross-hand/cross-embodiment tactile is the least covered axis.** HRDexDB has 4 embodiments but explicitly names tactile heterogeneity and non-uniformity as an unresolved limitation and has no policy baselines. roto 2.0 spans 4 morphologies but uses a *binary contact vector whose length varies per hand* — not a shared spatial representation. Bench2Dex is the only one with a **shared surface-aligned tactile map across 12 hand meshes**.
4. **No other benchmark splits robustness into invariance vs equivariance axes.** HT-Bench = one task-level OOD axis; RCT = held-out units; SoftVTBench = held-out initial states + lighting; roto 2.0 = none; HRDexDB = none. So Bench2Dex's two-axis framing (and its LSCR/safety diagnostics) has **no directly comparable baseline** among the seven.

### b.2 What "Tactile_Cross" means — decoded from the repo (no paper describes it)

**Answer: "Cross" = TacMap Cross-Attention, NOT cross-embodiment.**

Verified from `policy/GR00T_n15_Tactile_Cross/README.md`, whose first line reads `# GR00T N1.5 TacMap Cross-Attention`:

- **Architecture:** loads pretrained GR00T N1.5; **freezes the Eagle vision tower and the language model**; jointly trains the original action head, the DiT, and a **TacMap residual-correction branch**. DiT output action tokens = Query; tactile tokens = Key/Value; Q/K LayerNorm'd; fusion at **`post_dit`** (after DiT, before the action decoder). `out_proj` is **zero-initialized**, so at init the branch is an exact identity to the base GR00T output. Loss remains the original flow-matching loss. Whole-modality tactile dropout 0.3, with the residual gated to exactly zero on dropped samples.
- **Tactile input:** raw metric depth `robot/tactile/distance_along_normal_m/<site>` (float32 metres), normalised by `robot/tactile/meta/max_distance_m` (default 0.015 m): `depth = clip(depth_m, 0, d_max)/d_max`. Each site → shared CNN → 2×2 = 4 tokens + site/spatial embeddings. Default 240×240 input.
- **Contrast with `GR00T_n15_Tactile` (the sibling branch):** that one is *pre-DiT / VLM-fused* — a learned-query attention-pooled single tactile token is appended to the Eagle vision-language token sequence before the action head. Checkpoints from the two branches are **mutually incompatible**; the Cross branch must be retrained from the GR00T N1.5 base.
- **Data schema:** the old branch consumes `robot/tactile/tacmap/{site_name}` uint8 `[T,H,W]` resized to 120×120; the Cross branch consumes the *metric* `distance_along_normal_m` field, and the README states the quantised `tacmap` field "will not enter the policy."
- **Eval:** the launcher uses four channels named `none`, **`cov_only`**, `inv_only`, `inv_cov`. The paper names the analogous channels `None`, **`Equi.`**, `Inv.`, `Full` (`none`/`equi_only`/`inv_only`/`inv_equi`). ⚠️ Inference (medium confidence, not stated anywhere): repo `cov` = paper `equi` (covariance ≡ equivariance), i.e. the repo naming predates the paper's final naming.

**No paper describes this branch.** Instead, the repo's own `TACTILE_DESIGN_REVIEW.md` (dated **2026-09-08**, i.e. six days *before* the arXiv v1) is an internal engineering review that explicitly says the authors searched and **could not find an original "TouchRefine" paper** whose method details could be verified, and which benchmarks its design against VLA-Touch, Reactive Diffusion Policy, VT-Refine, and ReTouch. It self-diagnoses the branch's limits, including (verbatim in spirit): feedback latency of ~0.8 s of sim time because 16 queued steps are consumed before replanning; `pre_dit` Q comes from noised actions not yet fused with vision/language; only a single current tactile frame is read so contact *trends* cannot be estimated; 240×240 pooled to 2×2 may attenuate sparse local contact; the signal is CPD-filtered normal geometric distance + contact mask, so **the authors themselves state it cannot be claimed to measure normal force, shear, or friction**; and only an action flow-matching loss exists, so a tactile-intervention test is needed to prove the policy actually depends on touch. The doc's date and content make clear this is a **worked-on-but-unpublished internal line**, not a described method.

**On released weights (parent's observation "no released weights"):** consistent with what I can see — the repo README points checkpoints to `huggingface.co/Bench2Dex/policy_ckpt` and ModelScope, and the tactile forks require local `train.sh` runs; the Tactile README notes its training output directory is *not* auto-discovered by the eval launcher, so a checkpoint must be manually deployed. ❌ I could **not** verify the contents of the HF/ModelScope repos (network blocked, HTTP 000 from this sandbox). Treat "no Tactile_Cross weights released" as **unverified but plausible**.

### c.1 Direct answer to "does any of this use TACTILE as the privileged-to-deployable channel?"

**Almost, but in the opposite direction — and that matters.**

- The **dominant, well-established pattern is the reverse**: privilege = contact force / object pose / simulator physics, and **tactile is the deployable channel**. CableVLA (sim contact events → deployable TacSense), HydroShear (privileged contact force + object pose → deployable tactile shear), PTLD (privileged sim/real object pose+shape → deployable tactile estimator). TactiDex also privileges sim contact force in the critic, but the *deployed* policy explicitly does **not** use real tactile feedback.
- The **closest thing to a "tactile-as-privileged" reading** is CableVLA's TacSense: simulator-derived contact and slip/rolling event labels are used **only** to build the loss for a tactile encoder that then runs on raw tactile at deployment. But even there the privileged signal is *not tactile*; it is sim contact kinematics/event timing, and the deployable modality *is* tactile.
- **I found no work in which a simulated tactile signal acts as the privileged training-time teacher for a policy or representation that must run without it at test time** (e.g., simulated tactile supervising a vision-only student). Searches for this returned only the inverse-direction papers above.
- **I found no work that combines stage/progress supervision with tactile at all.** The stage-aware family (SARM, STARE, PACE, PRIMO R1, Bi-HIL, REDS, DrS) is uniformly RGB / joint-state / language / force based. The tactile family (ReTouch, CableVLA, TacSense, TactiDex, PTLD, HydroShear, roto 2.0) never predicts stages or progress. The intersection is empty in everything I fetched.

**Uncertainty:** DrS and REDS were characterised only through SARM's related-work section (marked ⚠️); I did not fetch them. STARE's ICLR 2026 status comes from a third-party wiki page — the OpenReview API returned 0 notes for the venue id I probed, so treat the venue as ⚠️ medium confidence, though the paper itself is on arXiv (2512.05107). STARE-VLA's identity vs the openreview `qBcgyxDeMM` PDF is inferred from a matching abstract fragment, not confirmed.

**Relevance to Bench2Dex (suggested by me, not by any source):** Bench2Dex already *has* the ingredients for the missing combination — per-stage executable predicates (hence LSCR), a surface-aligned tactile stream, and object/contact ground truth in sim. So "privileged sim predicates → deployable policy without predicates", with tactile as the privileged-to-deployable channel, is a gap that Bench2Dex's construction is unusually well-placed to fill.

## (d) What is NOT covered — 5 gaps, each with the searches that evidence it

1. **Nobody has used Bench2Dex at all — the benchmark's own tactile data has zero published consumers.**
   *Evidence I ran:* arXiv API `search_query=all:"Bench2Dex"&max_results=30` → **1 entry (the paper)**; Semantic Scholar `/paper/arXiv:2609.15726/citations` → **1 citing paper**, which turned out to be a co-author 3D-reconstruction paper citing it once in the reference list; grep for "Bench2Dex" in ME-Dex 1.0 (2609.21449), HiTac-WAM (2608.19574), CableVLA (2609.25606), ReTouch (2608.01824), PTLD (2603.04531) → **0 hits**; web searches `"Bench2Dex" follow-up 2026`, `"Bench2Dex" dataset used policy training 2027`, `Bench2Dex citation tactile cross-embodiment 2026` → only the paper/project page/mirrors. **Implication:** the ~1.3K demos, 12-hand shared tactile representation, and LSCR/safety suite are untouched — first-mover room, but also no external validation of the benchmark's tactile signal.

2. **The tactile-trained baselines that the repo contains are unpublished, and the paper's headline results are all non-tactile.** The paper reports ACT/DP/π0.5/GR00T N1.5 on vision+proprioception only, yet the repo ships `ACT-Tactile`, `GR00T_n15_Tactile`, `GR00T_n15_Tactile_Cross`, `GR00T_XE`; full-text grep of the paper for "cross-attention"/"Tactile_Cross"/"post_dit" → 0 hits.
   *Evidence I ran:* fetched paper HTML and grepped; GitHub contents API for `policy/` and both tactile directories; `TACTILE_DESIGN_REVIEW.md` (2026-09-08) which admits no verifiable reference paper exists for the design it is imitating ("TouchRefine") and lists its own unresolved confounds (feedback latency, no temporal tactile context, pooled 2×2 attenuation, distance-not-force semantics, no tactile-intervention ablation). **Implication:** the tactile→policy gain on Bench2Dex is *unknown and currently unreported* — anyone reporting a tactile improvement must first build the missing matched no-tactile baseline the doc itself asks for.

3. **The invariance/equivariance split is not comparable to anything else, so cross-benchmark robustness claims cannot be made.** None of the seven cited tactile benchmarks uses a two-axis invariance/equivariance decomposition: HT-Bench = one task-level OOD split; RCT = held-out material/category/sensor/position/sequence; SoftVTBench = held-out initial states + lighting + rigid-twin controls; roto 2.0 = none; HRDexDB = none; EgoTactile = object- and subject-held-out.
   *Evidence I ran:* full-text greps for `generaliz|held-out|unseen|distribution shift|invariance|equivarian` in each of roto2.txt, htbench.txt, hrdexdb.txt, tactidex.txt, softvtbench.txt; web searches `equivariance axis invariance axis benchmark manipulation policy evaluation 2026` → returned the Bench2Dex paper itself plus unrelated work. **Implication:** the two-axis framing is a genuine contribution with no precedent, but also no external baseline numbers — you cannot yet say "policy X is more equivariant than policy Y" against any published comparator.

4. **Cross-embodiment tactile unification is an acknowledged open problem that Bench2Dex addresses only in simulation.** HRDexDB — the closest real-world analogue — explicitly states tactile hardware specs "are not uniform across different robotic platforms", that tactile is *absent* for its human-hand and Allegro sequences, and that "future work must investigate unification strategies or latent representations that can normalize these disparate tactile modalities." roto 2.0 varies hand morphology but uses per-hand binary contact vectors, not a shared spatial map.
   *Evidence I ran:* full-text read of HRDexDB's Limitations section; roto 2.0's observation table (17/14/20/17 binary contacts vs 20/16/16/17 joints); searches `cross-embodiment tactile representation shared across dexterous hands policy learning benchmark` (→ ME-Dex 1.0, Li Auto, 18 Sep 2026, "Bringing Heterogeneous Tactile Sensing into World Action Modeling", which greps **0** for Bench2Dex and does not cite it). **Implication:** a 12-hand shared surface-aligned map is unique, but the sim→real status of that representation is untested and TacMap (its basis) has only been validated for a single in-hand rotation task.

5. **Tactile is essentially never the privileged-to-deployable channel, and is never combined with stage/progress supervision.** Every privilege→tactile paper runs the other way (CableVLA, HydroShear, PTLD); TactiDex privileges tactile-like sim contact forces but does not deploy tactile; no stage-aware method (SARM, STARE, PACE, PRIMO R1, Bi-HIL) touches tactile.
   *Evidence I ran:* full-text greps for `tactile|touch` across sarm_full.txt, pace.txt, starevla.txt, activecritic.txt, subtask.txt (Bi-HIL) → no tactile-policy usage; greps for `privileg` in cablevla.txt, hydroshear.txt, ptld.txt → the inverse pattern; searches `privileged simulation contact ground truth supervise tactile representation deployable`, `privileged tactile simulation RL actor critic deploy without contact ground truth 2026`, `tactile feedback subtask stage progress estimation manipulation policy 2026`, `"stage" OR "progress" estimation from tactile signals long-horizon manipulation stage classifier`. **Implication:** the specific combination you flagged — **privileged simulation predicates/contact ground truth supervising a representation that must run without privilege, with tactile as the transfer channel, on a stage-structured long-horizon task** — appears genuinely unoccupied.
