## 4. Deviations, fixes and caveats (read this)


- **torch cu128 everywhere.** The official env scripts pin `torch==2.0.0+cu118` (DP),
  `torch==2.5.1` (GR00T) and `jax[cuda12]==0.5.0` (pi0.5) — none of which have `sm_120` (Blackwell)
  kernels. All three were replaced: torch → `2.7.0+cu128`, jax → **`0.6.2`** (newest version that
  both keeps `jax.experimental.layout.DeviceLocalLayout`, which `orbax-checkpoint==0.11.1` imports,
  and ships Blackwell kernels: ≥0.7 removed the API, 0.5.x has no sm_120 kernel).
- **Split server/client forced.** The repo's `eval_double_env.sh` scripts hard-code the
  simulator-side conda env as `dex2bench`; ours is `bench2dex`, so `70_eval_dp.sh`,
  `72_eval_gr00t.sh` and `73_eval_pi05.sh` replicate that orchestration with correct env names and
  our four Isaac fixes (local `libGLU.so.1`, the lab proxy, the `omni.kit.registry.nucleus` override
  for the unreachable CloudFront registry, and `CUDA_VISIBLE_DEVICES`).
- **Robot USD emits unresolved-reference warnings for every `*/visuals` prim**, e.g.
  `Unresolved reference prim path @.../multi_iiwa7_with_sharpa_physics.usd@</visuals/left_index_fingertip>`.
  The released `multi_iiwa7_with_sharpa_base.usd` (21 MB, holds the meshes) references visual prims
  that the 19 KB physics-only USD does not contain. It appears identically in the ACT and DP logs,
  and our asset download matches the documented file count (52,764 files) — so it is an upstream
  asset characteristic, not something this deployment broke. It does mean some wrist-camera views
  may lack hand geometry, which is one candidate explanation for the ACT/task-26 shortfall.
- **Run-to-run variance is real.** Two identical smoke runs (same seed, same checkpoint) gave
  `latched_stage_completion_rate` 1.00 vs 0.25 for the same episode. Treat each cell as one sample.
- **GPU sharing.** Only GPU 2 was idle (the other three are pinned by other users); everything here
  runs on GPU 2, at most 3 Isaac instances plus 3 policy servers at a time.
- **Data location.** All data/weights live on `/mnt/public/datasets/bench2dex/` (NFS, symlinked into
  `~/bench2dex/`); only the conda environments and code are on `/home`.

### ⛔ Known upstream blocker: GR00T N1.5 cannot be evaluated as released


The released `Bench2Dex/New_Policy` GR00T checkpoints for these tasks contain only **4 files**
(`config.json`, `model-0000{1,2}-of-00002.safetensors`, `model.safetensors.index.json`) — verified
against the ModelScope repo tree, and `gr00t_n15/experiment_cfg` does not exist there at all.

But the code requires it:

* `policy/GR00T_n15/deploy_policy.py:127` → `_validate_local_checkpoint()` raises
  `FileNotFoundError` unless `<model_path>/experiment_cfg/metadata.json` is a file.
* `policy/GR00T_n15/src/gr00t/model/policy.py:110` → `_load_metadata(model_path/"experiment_cfg")`
  opens that JSON and validates the per-embodiment entry (`DatasetMetadata` = the state/action
  **normalization statistics** for the finetuned embodiment).

Those statistics are functionally required (they un-normalize the predicted actions), so fabricating
a `metadata.json` would produce silently wrong numbers — worse than not running. Note the official
`policy/GR00T_n15/eval_double_env.sh` auto-discovery would also pick this same directory (it only
checks `config.json` + `model-*.safetensors`), so the failure is upstream, not a mistake in this
run's arguments.

**Measured, not inferred:** starting the GR00T policy server against the real released checkpoint
exits **8 seconds** later with `exit=1` and exactly:

```
FileNotFoundError: GR00T_n15 local model_path must be the finetuned checkpoint root containing
experiment_cfg/metadata.json, got: .../policy_ckpt/26/multi_iiwa7_with_sharpa/gr00t_n15.
Do not pass the base HF model or a checkpoint subdirectory unless it includes experiment_cfg.
```

so this stage fails fast (it does not hang the pipeline) and the failure is captured in
`_deploy_logs/72_gr00t_server_*.log`.

**To unblock GR00T you need one of:** the `experiment_cfg/metadata.json` for these checkpoints from
the authors; or regenerate it from the finetuning data (`src/gr00t/utils/experiment.py` writes
exactly this artifact during training and the corpus appears to be the same `replay-generalization`
HDF5s we already have); or re-finetune GR00T locally.
